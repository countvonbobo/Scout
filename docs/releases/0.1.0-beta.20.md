# Scout 0.1.0-beta.20

Beta 20 replaces the dynamic category tabs with a single Jobs triage inbox and a Shortlist tab, folds in a batch of swarm-reported runtime fixes, and fixes five further issues: editable scan schedules, the Reports desktop layout and nested headings, reachable tailored-CV controls, independent CV save/render actions, and per-opportunity tailored CV folders.

## Jobs triage inbox and Shortlist

- Replaces the dynamic per-category "lane" tabs with a fixed navigation: **Jobs · Shortlist · Pipeline · All · Reports · CV**.
- **Jobs** is a triage inbox showing only newly found opportunities (`status:'new'`), highest score first. Each card carries a colour tag naming its search category; the colour comes from the category's position in the user's configured categories, so it works for any number of categories without hardcoding.
- Each card offers one-tap **No** (dismisses, with a roughly six-second **Undo** toast) and **Yes, shortlist** (moves the role to a new `shortlist` status). Tapping the card body still expands full detail, including the source advert.
- The new **Shortlist** tab offers **Remove** (dismisses with undo, same as Jobs) and **Create tailored CV**; marking a shortlisted role as applied moves it to **Pipeline** as before.
- Dismissed roles stay in the tracker and the **All** tab and are never re-surfaced by a later scan.

## Runtime and UI fixes reported by swarm audit

- `DELETE /api/setup/proposal` no longer requires a JSON content-type header to accept the request.
- `setCommute` can clear a previously set field again: an empty string is treated as "unset" rather than being ignored (`||` replaced with `??`).
- Report Markdown links are no longer double-escaped, so link text and targets render correctly.
- `parseChecksums` tolerates a trailing space after the hash and an optional `./` prefix on the path.

## Scheduled scans

- Fixes configured scan schedules becoming stuck read-only after an unhealthy, stale or skipped run. The healthy-supervised-scan requirement now gates only the *first* enablement of automated scans; once a job exists, its time, days and model can always be changed, and it can be disabled or re-enabled, regardless of a later run's health.
- An existing setup is no longer described to the user as a first run.

## Reports

- Fixes the Reports desktop layout: the report-date navigation stays a fixed 220px vertical sidebar instead of collapsing the report body into a narrow column at wide viewport widths.
- Nested Markdown headings (`###` and deeper) in a report now render as headings instead of showing the raw `###` marker as text.

## Tailored CV controls

- The CV tab now opens at the top instead of inheriting whatever scroll position the previous tab was left at.
- The tailored-CV selector can no longer push its confirm button off-screen for a long opportunity label.
- Renames the CV library actions for what they actually do: **Create tailored CV** is now **Review CV options**, and its confirm control is now **Start tailored CV**.

## CV save and render

- **Save changes** and **render PDF** are now separate actions with independent states. Saving no longer forces a PDF render, and rendering no longer rewrites (and re-checkpoints) the saved source.
- If a render fails after a successful save, Scout now explicitly confirms the saved source is intact rather than leaving the outcome ambiguous.

## Tailored CVs are per-opportunity

- Tailored CVs are now keyed by the tracked opportunity instead of the company, so two roles at the same employer each get their own CV folder and no longer collide.
- CV folders created before this release are left exactly where they are on disk: nothing is moved, renamed or deleted. An existing folder is still readable and is only reused in place after an explicit prompt that names whose CV it is; declining starts a fresh CV tailored to the newly selected role.

## Upgrade and compatibility

- No workspace schema migration, provider sign-in, or backup-format change is required.
- Existing tailored CV folders remain in their original location and are reused only after confirmation, as described above.
- Release tags are immutable. A published tag is never moved; a correction is published as a new version.
